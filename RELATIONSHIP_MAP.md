## 1. Canonical Entity Records

### 1.1 Customers / Contacts
- **Collection:** `contacts` (in `companies/{companyId}/contacts`)
- **Type Definition:** `src/features/crm/types/contacts.types.ts` - `Contact`
- **Primary ID:** `id` (string, auto-generated by Firestore)
- **Service:** `src/features/crm/api/contacts.service.ts` - `ContactsService`
- **Key Fields:**
  - `id`: Stable unique identifier
  - `entityType`: "individual" | "company" | "establishment" | "government" | "non_profit" | "bank" | "media" | "influencer" | "other"
  - `firstName`, `lastName`, `fullName`: Individual names
  - `accountName`, `legalName`: Commercial/organization name
  - `email`, `phone`, `whatsappPhone`: Contact information
  - `commercialRegister`, `taxNumber`, `unifiedNumber`: Legal identifiers
  - `assignedTo`: Employee ID (owner/relationship manager)
  - `associatedContacts`: Array of contact persons with `isPrimary`, `isDecisionMaker`
  - `relationships`: Array of relationship types (lead, active_client, vendor, etc.)
  - `classification`: Dynamic classification (actual_client, potential_lead, callback)
  - `financialInfo`: Payment terms, VAT registration, credit limit
  - `crmSalesInfo`: Sales context (sector, expected budget, interested services)
- **Tenant Scope:** Scoped to `companies/{companyId}` via CRM collection structure
- **Referenced By:**
  - `Deal.contactId` (required for active deals)
  - `Contract.contactId` (in both top-level and `form.contactId`)
  - `Task.contactId` (direct link or via contract/deal)
  - `Invoice.customerId` (link to customer for billing)

## 3. Lifecycle Flow

### 3.1 Sales to Delivery Flow
1. **Lead** → **Contact** (conversion)
2. **Contact** → **Deal** (deal creation with contactId)
3. **Deal** → **Contract** (contract creation with dealId and contactId)
4. **Contract** → **Tasks** (service items converted to tasks with contractId, dealId, contactId)
5. **Tasks** → **Task Completion** (status changes to "done")
6. **Contract/Deal** → **Invoice** (invoice creation with contractId/dealId/contactId)
7. **Invoice** → **Payment** (payment recording with invoiceId)
8. **Payment** → **Journal Entry** (accounting posting via voucher)

### 3.2 Relationship Preservation Rules
- **Never rely on names:** Always use stable IDs (contactId, dealId, contractId, taskId)
- **Cascade references:** When a contract is created from a deal, preserve both contractId and dealId in downstream tasks
- **Multi-path resolution:** Tasks can be linked via direct contactId OR via contractId OR via dealId
- **Denormalization strategy:** ContactDetailPage shows tasks filtered by all three paths (contactId, contractId, dealId)

## 5. Data Integrity Rules

### 5.1 Multi-Tenant Isolation
- All tenant-scoped collections are under `companies/{companyId}/`
- Firestore rules enforce `companyId` matching user's company membership
- Users collection is root-level but has `companyId` field for association

### 5.2 Referential Integrity
- **Soft references:** Foreign keys are stored as strings without enforced constraints
- **Orphan prevention:** UI prevents deletion of records with active references (not enforced at database level)
- **Cascade deletion:** Not implemented - manual cleanup required

### 5.3 Idempotency
- **Contract → Task conversion:** Uses `convertedToTasks` flag to prevent duplicate task generation
- **Payment recording:** Transaction-based atomic operations prevent double-posting
- **Invoice posting:** Journal entry ID stored to prevent re-posting
